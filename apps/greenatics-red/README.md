## Arquitectura

- Runtime FastAPI separado del sitio institucional estático.
- PostgreSQL dedicado para RED en el proveedor general Greenatics. `DATABASE_URL` debe apuntar a la base de RED; no reutilices la URL de Huella u OPS. `DATABASE_SCHEMA` debe quedar vacío en staging/producción: RED detiene el arranque antes de ejecutar migraciones si se configura un esquema compartido. El esquema sigue disponible solo para pruebas locales aisladas de migraciones.
- SQLAlchemy 2 y migraciones Alembic.
- Evidencias mediante un adaptador privado. Desarrollo usa filesystem; el blueprint de hosting usa un bucket S3 compatible dedicado para RED. Drive personal almacena copias ZIP independientes, no los archivos operativos de captura.
- OAuth web de Google para subir respaldos a una carpeta de la cuenta personal que autorice la conexión.
- El blueprint `render.yaml` sigue el patrón Docker en Render que ya está documentado para Calcula tu Huella y fija `plan: free` para que un preview no active cómputo pago por omisión. Es solo para demostración sintética: Render Free duerme tras inactividad, tiene filesystem efímero y no admite disco persistente; la base PostgreSQL gratuita vence a los 30 días y no incluye backups. No es un destino de piloto. La versión operativa requiere un runtime y servicios persistentes dedicados ya disponibles dentro del presupuesto autorizado; faltan hostname, base RED dedicada, bucket privado y secretos. Declara `RED_PUBLIC_SITE_ORIGINS` como valor manual y mantiene `RED_PUBLIC_ACCESS_ENABLED=false` hasta cerrar el gate público. Consulta las [limitaciones oficiales de Render Free](https://render.com/docs/free) y [discos persistentes](https://render.com/docs/disks).

Las solicitudes HTTP tienen un límite de cuerpo de cuatro veces `RED_MAX_UPLOAD_MB` más 4 MiB para campos y multipart. El límite se aplica antes de que Starlette parsee o vuelque adjuntos a disco, incluyendo cuerpos sin `Content-Length`; las rutas conservan también los límites por archivo, por guardado y por cantidad de adjuntos. El almacenamiento registrado de evidencias tiene además topes agregados configurables: `RED_MAX_EVIDENCE_TOTAL_MB` (1.024 MB por defecto) y `RED_MAX_EVIDENCE_PROJECT_MB` (256 MB por expediente); una verificación transaccional común cubre carga, reintentos y restauración. Estos topes limitan la aplicación y no prueban la capacidad del proveedor de almacenamiento. El dashboard de Administración RED muestra uso y disponibilidad total y por expediente; los perfiles de proyecto no reciben esa vista global. Si el tope se acerca o rechaza una carga, la administración puede revisar el consumo registrado y coordinar un cambio de configuración; antes de liberar espacio debe conservarse la evidencia según la política aprobada. El valor configurado no sustituye la comprobación de capacidad del proveedor.

RED verifica en el servidor que la extensión concuerde con la firma básica de PDF, JPEG, PNG o HEIF, o con la estructura ZIP esperada de DOCX/XLSX; para CSV/TXT rechaza bytes NUL. El MIME se deriva de la extensión permitida y no del encabezado del navegador. Esta comprobación detecta archivos vacíos, incompatibles o con firma/formato evidente incorrecto; no decodifica completamente cada formato ni es un análisis antivirus o antimalware. Los adjuntos siguen siendo contenido no confiable y se almacenan en el backend privado configurado.

El login pausa durante diez minutos la combinación de cuenta e IP después de seis fallos y la IP después de 30 fallos dentro de una ventana de diez minutos. En staging/producción exige `TRUSTED_CLIENT_IP_HEADER=CF-Connecting-IP`; el blueprint Render lo declara y el proceso Uvicorn no confía globalmente en encabezados `X-Forwarded-*`. Falta comprobar en staging que la cabecera llega exclusivamente desde el proxy confiable. Las claves se guardan como HMAC y no contienen la IP en claro, pero son seudónimas. Los contadores usan un UPSERT atómico para conservar incrementos concurrentes en SQLite y PostgreSQL; la concurrencia se probó localmente en SQLite y el SQL se compiló para ambos motores, pendiente de ensayo PostgreSQL en staging. RED elimina filas de throttling con más de 24 horas al abrir/enviar el login; `cleanup-login-throttles` permite limpieza manual. No hay scheduler configurado, por lo que la depuración continua no está garantizada.

Los intentos con una cuenta inexistente o inactiva también ejecutan PBKDF2 usando un hash señuelo. Esto evita que esas rutas omitan deliberadamente el costo criptográfico y entreguen una señal de tiempo evidente sobre la existencia de la cuenta; no constituye una garantía matemática de tiempo constante.

**Límite de infraestructura vigente:** Render Free sirve para previews, no para persistencia operativa: duerme después de inactividad y su filesystem local es efímero; Render Postgres Free vence a los 30 días y no incluye backups. Supabase Free podría probarse como backend independiente solo para staging sintético: su base puede pausarse tras una semana de baja actividad, tiene límites de capacidad y no incluye backups automáticos ni SLA. La clave S3 de Supabase abarca todos los buckets del proyecto, por lo que el adaptador de RED requiere un proyecto dedicado y no debe conectarse al `greenatics-ops` de Huella/OPS. No uses estos niveles gratuitos para capturar datos de campo. Con el presupuesto $0 vigente, no se aprovisiona ningún servicio en esta tarea. Fuentes primarias: [Render Free](https://render.com/docs/free), [Supabase Free](https://supabase.com/pricing), [pausas](https://supabase.com/docs/guides/platform/free-project-pausing), [backups](https://supabase.com/docs/guides/platform/backups), [S3 Authentication](https://supabase.com/docs/guides/storage/s3/authentication).

`RED_OPERATIONAL_WRITES_ENABLED` está cerrado por defecto en todos los entornos. Para QA local deliberado se puede habilitar explícitamente solo con datos sintéticos; no uses el entorno local para datos reales antes de aprobar los gates. En staging o producción, además se exigen `RED_PRIVACY_APPROVED=true` y `RED_SUPERVISED_PILOT_APPROVED=true`; ambas permanecen `false` por defecto en `render.yaml` y deben cambiarse en el gestor de secretos solo tras archivar las aprobaciones correspondientes. Aunque se activen las escrituras, la aplicación las ignora mientras falten HTTPS, PostgreSQL, almacenamiento persistente, hosts permitidos, OAuth de Drive con redirección HTTPS a `/drive/callback` en el mismo origen o cualquiera de esas dos aprobaciones. El acceso público sigue siendo una compuerta separada. Cuando las escrituras están cerradas, la interfaz muestra un aviso de solo lectura; cada persona puede abrir, con campos deshabilitados, los formularios autorizados para su perfil. Los demás se marcan como no disponibles y el servidor rechaza su acceso. Todos los POST operativos siguen bloqueados y no persisten datos. También se rechazan cambios de proyecto, PMIRS, cuentas/membresías, invitaciones, Drive y respaldos, incluido el callback OAuth y el comando programado `backup-to-drive`. Inicio/cierre de sesión, recuperación de contraseña, creación inicial de administrador, siembra de expedientes vacíos y restauración aislada siguen disponibles.

D04-004 es una subtabla; las demás relaciones/subtablas/controles derivados aún pendientes requieren modelo o protocolo técnico. El perfil de campo puede registrar una novedad en P-14 y solo editar sus campos de novedad; las referencias de guía y contactos son de solo lectura. Captura solo valores respaldados, registra método/fuente y deja pendiente lo desconocido. No hay modo sin conexión.

P-02 ahora ofrece subregistros repetibles para el equipo de apoyo (P02-003), gestores/recicladores reportados (P02-005) y capacitaciones previas (P02-009). Cada campo se mantiene opcional como indica el maestro; hay un máximo técnico de 50 filas. El texto libre histórico se conserva marcado para revisión. P02-005 no infiere habilitación jurídica y P02-009 no presenta antecedentes como capacitación del PMIRS nuevo.

Los campos D02-011, D05-009 y D10-003 convierten las opciones confirmadas del maestro en multi-selección y ofrecen un área aparte para describir hechos asociados. La vista, edición y exportación conservan el texto junto al conteo normal de archivos; no se deben escribir datos personales, códigos de acceso ni enlaces públicos en la referencia. ## Gate del enlace público

El enlace externo de la página estática `/red/` permanece oculto hasta que el navegador obtiene una respuesta vigente y válida de `GET /api/ready`. El endpoint devuelve 200 solo en un entorno `production` con el flag habilitado, configuración productiva completa, los cuatro expedientes precargados con slugs, nombres y ubicación Bello/Antioquia esperados, una cuenta administradora activa, conexión personal de Drive con token cifrado descifrable y un ZIP exitoso en la carpeta Drive actualmente conectada, completado dentro de las últimas 48 horas y registrado con hash y tamaño. Las fechas futuras, una carpeta Drive anterior y un respaldo antiguo no mantienen la aplicación lista. No devuelve correos, IDs de Drive ni detalles de configuración. La respuesta lleva `Cache-Control: no-store` y permite CORS únicamente desde los orígenes HTTPS listados en `RED_PUBLIC_SITE_ORIGINS`; sin CORS, sin respuesta o con cualquier otro estado, el enlace queda oculto. El navegador vuelve a comprobar al abrir la página, al regresar a ella y cada minuto. El flag no sustituye la aprobación humana del gate: habilítalo únicamente después de probar en staging el acceso, el respaldo y la restauración, y cerrar privacidad, protocolo técnico/SST y el ensayo supervisado.

Cuando exista el runtime, configura su origen HTTPS en `NEXT_PUBLIC_RED_APP_URL` al compilar el sitio. Esta URL es pública, no un secreto; no se publica un enlace directo desde ella. El sitio consulta `/api/ready` desde el navegador y muestra **Abrir entorno GREENATICS Red** solo cuando el runtime responde `ready`, con cuatro expedientes y respaldo Drive verificado. El enlace de la estación sintética se conserva como muestra. El export estático puede usar esta verificación del navegador, por lo que no requiere un runtime Next.js; el FastAPI RED sí es un servicio independiente. `qa:runtime-preflight` comprueba también el endpoint de readiness para cada origen HTTPS configurado.

## Evidencias y respaldos

Los eventos nuevos de auditoría omiten copias de notas libres, correos, referencias y nombres de archivo cuando el dato ya se conserva en el registro operativo correspondiente. La cronología de actividad del proyecto muestra actor, acción y fecha sin exponer el detalle bruto del evento. La creación de backups también sanitiza esos campos en eventos históricos y la restauración aplica el mismo filtro a archivos legados; la base local y ZIP ya emitidos no se reescriben. Los nombres y correos de invitaciones se exportan como valores genéricos porque sus tokens no se restauran y las pendientes siempre vencen en la recuperación. Esto no establece retención: el inventario, acceso y eliminación del log deben aprobarse antes de cargar datos reales.

El respaldo vigente usa esquema 14 e incluye el registro administrativo mínimo de solicitudes de privacidad y el estado de identidad cotejado con una fuente de cada copropiedad. La tabla de privacidad tiene campos de metadatos, responsables y referencias externas opacas; no cuenta con campos para identidad, contenido de solicitudes/respuestas o adjuntos. RED limita las referencias a caracteres de código y requiere letras y números, pero son ingresadas por usuarios: no deben usarse para copiar datos personales o texto libre. La identidad territorial se confirma por separado, con dirección, referencia opaca de la fuente, cuenta revisora y fecha; queda pendiente por defecto y administración RED puede administrarla globalmente y el perfil Administración PH puede confirmar o guardar solo su propio expediente; el perfil que hizo el cotejo queda registrado. La vista de auditoría conserva actor, hora UTC y tipo/transición de cambio, sin valores de referencias en el detalle. RED no calcula términos legales ni resuelve solicitudes por sí mismo. La aprobación de responsables, canales, aviso, retención/eliminación y el procedimiento de derechos permanece pendiente. Los ZIP también conservan los datos personales que existan en cuentas, formularios, auditoría y evidencias; aplicar a esos archivos el control de acceso y retención que se apruebe.

La migración 0015 agrega autorizaciones de visita por copropiedad, la 0016 claves idempotentes para cargas independientes de evidencia y la 0017 la confirmación de identidad territorial, la 0018 permite a cada Administración PH confirmar solo su unidad y guarda el perfil responsable, y la 0019 serializa las cargas para aplicar cuotas agregadas de evidencia. Antes de habilitar escrituras para formularios de campo, administración RED registra referencias opacas de acceso, privacidad, método técnico y SST, confirma que revisó los soportes externos y fija su fecha de vencimiento. La app no almacena esos documentos ni determina su validez jurídica o técnica. La autorización expira por fecha y puede revocarse con una causa controlada; ambos cambios quedan auditados. Las escrituras, ediciones, firmas y cargas de evidencia para D-03–D-14 y P-14 se rechazan en servidor si falta una autorización vigente, sin bloquear D-01/D-02 para el alistamiento previo. Los backups de esquema 14 incluyen autorizaciones, historial, claves de reintento de evidencia, identidad y perfil que la confirmó; los esquemas 1 a 13 siguen siendo compatibles.

Los campos `Archivo` e `Imagen` del maestro abren cargas desde cámara o dispositivo y asocian cada archivo con su registro y código de campo. En un registro en estado `RAW` también se puede adjuntar evidencia general desde el detalle. Cuando el registro está en revisión, validado o devuelto a corrección, la carga directa queda bloqueada: consulta o crea una nueva versión, adjunta allí los archivos (generales o de campo) y envíala a QA/QC. Esa edición conserva los archivos anteriores, registra la nueva versión y, si modifica una fuente de Línea Base o un equipo D-13 con pesajes validados asociados, reabre las revisiones dependientes. Los archivos aceptan PDF, JPG, PNG, HEIC/HEIF, DOCX, XLSX, CSV y TXT; el máximo es `RED_MAX_UPLOAD_MB` por archivo (20 MB por defecto), hasta 12 por guardado y cuatro veces ese máximo en total por guardado. Los archivos generales no sustituyen un soporte que el catálogo exige en un campo específico. Las cargas se conservan al editar y no se comparten automáticamente. Se guardan fuera de la web pública, con hash SHA-256 y descarga autenticada; la emisión de cada descarga se registra en auditoría. En S3, RED entrega enlaces firmados de descarga con vigencia de cinco minutos después de revisar la membresía. Antes de validar un registro, el autor puede retirar sus propios archivos; consultoría RED, revisoría y administración RED pueden retirar cualquiera del registro. El retiro se audita y elimina el objeto. Un registro validado bloquea el retiro hasta crear una nueva versión para revisión. Mantén el bucket privado, bloquea acceso público y limita las credenciales del runtime al bucket RED; no expongas credenciales S3 al navegador.

Los respaldos actuales usan esquema 14; verifican manifiesto, conteos, relaciones, firmas, referencias operativas, de privacidad y de autorización de visita, datos de identidad, evidencia y claves de reintento para formularios, ediciones, avances PMIRS y cargas independientes de evidencia. La restauración conserva compatibilidad con esquemas 1 a 13 y aplica valores seguros a los campos incorporados después. La creación y verificación limitan los metadatos JSON expandidos a 256 MiB y la evidencia al total configurado en RED antes de leerla; la verificación local aislada no demuestra todavía restauración en PostgreSQL, Drive o staging.

Desde **Drive y respaldos**, un administrador puede crear un ZIP bajo demanda. Incluye JSON de los datos de RED, versiones, auditoría, membresías, invitaciones sin tokens, evidencias y manifiesto de integridad. Omite hashes de contraseñas y tokens OAuth. El ZIP se verifica antes de subirlo y su SHA-256 queda en el registro de respaldo.

El panel presenta la autorización guardada como **Pendiente de comprobar**: una conexión registrada no demuestra que Google aún acepte el token. La vigencia se confirma al crear o descargar un respaldo. Si falla la creación, RED vuelve al historial, conserva el estado fallido y orienta al administrador para revisar la autorización. Si el intercambio OAuth falla o se cancela, RED también vuelve al panel con un mensaje seguro y permite reintentar cuando la configuración esté lista. Desde allí puede volver a autorizar Drive; la acción conserva la carpeta si se usa la misma cuenta, y sigue protegida por el gate operativo y la configuración OAuth. El mensaje visible no expone el diagnóstico interno.

Después de la carga, RED compara el tamaño, el SHA-256 devuelto por Drive, el MIME `application/zip` y la carpeta de destino con el archivo y la conexión esperados. La API de Drive documenta `size`, `sha256Checksum`, `mimeType` y `parents` como metadatos del recurso [File](https://developers.google.com/workspace/drive/api/reference/rest/v3/files). Si la respuesta de carga no trae esos campos, RED los consulta por ID. Una discrepancia o una verificación no disponible deja el respaldo en estado fallido; si Drive ya devolvió un ID, RED lo conserva en el historial para inspección y no lo acepta para `/api/ready`.

La CLI permite crear, descargar y verificar respaldos Drive; también permite programar la misma rutina de carga en el scheduler del hosting. Después de conectar Drive y crear el administrador, configura el correo de esa cuenta como variable `RED_BACKUP_ACTOR_EMAIL` y ejecuta diariamente (por ejemplo, 02:00 UTC):

```sh
python -m app.cli backup-to-drive --actor-email "$RED_BACKUP_ACTOR_EMAIL"
```

El blueprint de referencia no activa un cron porque el proveedor/servicio de hosting de RED aún no está confirmado. Hasta configurar el scheduler, la única frecuencia activa es manual desde el panel. No se borran respaldos automáticamente; define retención antes de acumular copias indefinidamente.

### OAuth de Google para el Drive personal

La aplicación solicita `openid email https://www.googleapis.com/auth/drive.file`; no pide acceso completo a Drive. Google clasifica `drive.file` como alcance no sensible y permite crear archivos propios de la aplicación. RED desactiva la autorización incremental, exige que la respuesta de autorización y las renovaciones confirmen exactamente esos tres scopes, y falla de forma cerrada ante permisos ausentes o adicionales. Si un refresh token antiguo conserva un acceso más amplio, no se usa: revoca el permiso anterior de GREENATICS RED en Google y vuelve a conectar. Mantén este alcance mínimo; no lo amplíes a `drive` o `drive.readonly` para facilitar la configuración. Revisa [permisos de Drive](https://developers.google.com/workspace/drive/api/guides/api-specific-auth?hl=es) y la guía para [examinar los alcances concedidos](https://developers.google.com/identity/protocols/oauth2).

Configura la audiencia OAuth como externa cuando la cuenta autorizante sea personal. Mientras el estado de publicación siga en **Testing**, los refresh tokens vencen a los 7 días porque RED solicita también `drive.file`; solo se exceptúan aplicaciones que piden exclusivamente `openid`, correo y perfil. Ese modo sirve para pruebas temporales con el correo autorizado como tester, pero no para un respaldo desatendido ni para mantener `/api/ready` con copias frescas. Antes de habilitar el scheduler operativo, publica el cliente OAuth y completa la verificación básica aplicable a `drive.file`; revisa la marca y los datos del consentimiento, y confirma en staging que el refresh token sigue funcionando, se crea `GREENATICS RED - Respaldos` y completa el ciclo de respaldo/verificación/restauración. Referencias oficiales: [duración de refresh tokens y OAuth](https://developers.google.com/identity/protocols/oauth2), [verificación de alcances de Drive](https://developers.google.com/workspace/drive/api/guides/api-specific-auth?hl=es). Si el cliente permanece en Testing, registra la reconexión manual cada siete días y no presentes el respaldo programado como disponible.


Para seleccionar uno concreto, añade `--backup-id <id-del-registro-red>`. La descarga no cambia el archivo de Drive y registra el acceso en auditoría. Conserva la copia local de acuerdo con la política de retención después de completar la recuperación.

```sh

```

Para restaurar una copia, prepara primero una base RED nueva y vacía y configura el backend de almacenamiento de recuperación. La CLI solicita la contraseña nueva sin escribirla en el historial. La restauración automatizada a una base y almacenamiento sintéticos vacíos forma parte de las pruebas. - `/projects/{id}/records/export.csv`: exportación de los registros del expediente en filas campo/valor, disponible para administración RED, consultoría, administración PH y revisión; queda auditada y limitada al proyecto.

## Sandbox desechable DEMO para practicar el flujo de campo

Para recorrer captura, revisión y exportaciones sin registrar permisos ficticios en las cuatro copropiedades, ejecuta desde `apps/greenatics-red`:

```sh
.venv/bin/python scripts/run_synthetic_field_demo.py
```

Crea una base SQLite temporal e independiente. Alembic siembra inicialmente los cuatro expedientes vacíos; antes de sustituirlos por un único proyecto `DEMO`, el lanzador comprueba que no haya usuarios ni información de trabajo y que los cuatro proyectos sigan intactos. Rechaza bases distintas o personalizadas. El proyecto, seis cuentas sintéticas, cinco perfiles de proyecto, la autorización ficticia `DEMO-*` y una acción asignada existen solo para practicar en ese sandbox. La semilla crea un programa, un indicador y una acción con sus relaciones, fechas, responsable, criterio de cierre y evidencia esperada; cada objeto conserva una revisión inicial y eventos de creación/revisión por los perfiles sintéticos correspondientes. La Línea Base permanece sin aceptar para que el operario vea el bloqueo de avance y pueda practicar la carga de evidencia, no para simular una operación real. La autorización y los objetos DEMO no acreditan acceso, privacidad, método, SST, diagnóstico ni aceptación real.

El modo normal mantiene la Línea Base pendiente. Para practicar además el avance de una acción, inicia una instancia desechable con una Línea Base y soportes ficticios validados por el seed de capacitación. Añade `--with-progress-history` para precargar dos avances sintéticos visibles en PMIRS Studio (requiere `--full-training-scenario`):

```sh
.venv/bin/python scripts/run_synthetic_field_demo.py --full-training-scenario
```

Para el historial actualizado:

```sh
.venv/bin/python scripts/run_synthetic_field_demo.py --full-training-scenario --with-progress-history
```

El home y PMIRS Studio explican que esa aceptación no corresponde a una copropiedad real. Habilita practicar el recorrido de acción asignada, carga de evidencia y avance, además de crear una versión PMIRS, enviarla a revisión, aprobarla, firmarla con reautenticación y consultar sus salidas HTML, PDF y DOCX en pruebas aisladas.
